# Chunk Size 消融实验（中文 CMRC 语料，2026-10-31）

## 一、设置

- 语料：CMRC2018 文章 2,403 篇（与检索评测同一份）
- 切块：200 / 400 / 800 / 1600 字符，overlap = 20%
- 每个配置单独建 Milvus collection（dense 768 + BM25 sparse），同一 embeddinggemma-300m
- 评测：同一批 100 条中文 query，doc 级 gold，top-20，按 doc_id 去重后计算 R@k / nDCG@10 / MRR@10

## 二、结果

| chunk 字符 | overlap | chunks | 平均长度 | dense nDCG@10 | hybrid nDCG@10 | hybrid R@10 | hybrid MRR | 入库耗时 |
|---|---|---|---|---|---|---|---|---|
| 200 | 40 | 8,774 | 166.6 | **0.9375** | **0.9678** | 0.99 | **0.9603** | 54.6s |
| 400 | 80 | 4,467 | 308.0 | 0.9115 | 0.9609 | 0.99 | 0.9508 | 67.8s |
| 800 | 160 | 2,651 | 474.9 | 0.9182 | 0.9662 | **1.00** | 0.9550 | 62.7s |
| 1600 | 320 | 2,403 | 507.4 | 0.9165 | 0.9639 | **1.00** | 0.9517 | 58.8s |

（注：1600 字符时多数文章本身不足 1600 字，平均块长 507，接近不切块；chunk 数回落到文章数。）

## 三、结论（如实）

1. **在本语料上，chunk size 对检索指标影响很小**：hybrid nDCG@10 全部落在 0.961~0.968，极差 0.7 个点；100 条 query 下这个差异在统计噪声内（CI 约 ±3 点），**不能据此断言 200 最优**。
2. **dense 对 chunk size 更敏感一点**：200 字符 0.9375 vs 400 字符 0.9115（差 2.6 点），方向符合直觉（短块主题更集中），但同样需要更多 query 才能确认。
3. **召回饱和**：doc 级 gold + 每篇文章多 chunk，导致 R@10 接近 1.0，区分度不足。要真正比较 chunk size，需要 **chunk 级 / answer span 级 gold**，或者直接评"生成答案质量"。
4. **工程代价**：200 字符产生 8,774 chunks（约为 800 字符的 3.3 倍），索引体积、入库时间、每次检索返回的上下文碎片都更多；800/1600 更省，但单块上下文更杂。
5. **EN 语料不适用**：HotpotQA 段落本身就是自然段（平均 ~550 字符），不存在切块自由度；等接入 PDF/DOCX 长文档后再做 EN chunk size 实验。

## 四、建议

- 保持当前 **800 字符 / 160 重叠**（中文）：检索指标与 200 差 0.002（噪声内），但上下文更完整、chunk 数更少；
- 真正需要调 chunk size 的时机是**生成质量评测**（答案是否被切碎、引用是否完整），而不是 doc 级召回；
- 后续接 LangGraph 生成链路时，把"chunk 200 vs 800"作为生成层消融的一个维度重跑。
